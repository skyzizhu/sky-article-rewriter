# 技术说明、研究解读与教程

## 先区分读者任务

想理解“是什么、如何运行、为什么这样设计”，走说明路径；想完成“安装、配置、实现、排错”，走教程路径。两者混合时，先为操作提供最少解释，完整原理放在不会打断步骤的位置。没有操作目标的文章不强行添加教程。

## 技术说明：从问题进入机制

1. 找出技术在解决什么具体问题，以及原文限定的对象和场景。
2. 列出后续理解必须依赖的概念，按首次使用顺序解释。首次用日常语言说明，再保留准确术语；不能靠替换成另一个陌生词完成解释。
3. 展开输入、处理、输出或因果过程；区分原文实际流程与为解释制作的简化模型。
4. 对最难的机制按需用熟悉案例类比，指出对应关系和差异，再回到技术对象。
5. 给出原文已有的适用范围、代价和不确定性，不为了“深入”添加无关架构细节。

例如，将“缓存通过复用结果减少重复计算”解释为：同一个结果再次被请求时，系统可以先尝试取用此前保存的结果，减少重新计算。随后说明原文中的更新条件；不能类比成“永远不用再算”。

研究内容另外核对：研究对象、样本、方法、比较对象、指标、结果与解释是否分开。作者推测的原因不写成实验已证实的机制，局部结果不扩成所有场景。原文缺失的方法信息直接说明，不替它补实验。

## 技术教程：保证跟着做时仍然成立

内部为每一步记录“前置条件—操作—原文给出的预期结果—后续依赖”。依照依赖排序，不为叙事效果挪动初始化、安装、验证等必要步骤。

| 内容 | 改写动作 |
|---|---|
| 环境、版本、权限、依赖 | 原文给出且影响操作时保留；未给出则不猜 |
| 命令、代码、参数、文件路径、单位 | 保留精确形式，不因口语化擅自改名、删参数或换语法 |
| 步骤解释过于简略 | 在操作前说明目的，操作后说明原文可确认的结果 |
| 大段原理打断操作 | 必要解释就近保留，延伸机制后移 |
| 缺失步骤或结果 | 标明缺失，不能宣称教程已完整可运行 |
| 示例代码或占位值 | 明确其示例性质，保留占位说明，不写成用户真实配置 |

改写原文教程不等于实际执行。用户未要求操作时不安装依赖、不运行命令，不声称测试通过。原文代码如有疑似问题，说明疑点；需要修复时明确区分原版和修正版，并验证有依据的改动。新增或更新外部技术事实时查阅相应官方文档，不能将旧文悄悄改成最新版本教程。

可用结构为“目标与必要准备 → 按顺序操作并解释 → 确认结果 → 原文已有的常见问题”。没有原文依据的结果截图、故障现象和排错步骤不能补写成事实。

交付前检查：类比是否失真，关键限定是否消失，代码和步骤是否保持准确，讲解中是否过早引入未解释术语。
